## Why it can't reach them via the daemon either

`run.ts:887` starts the daemon with `ceremonyTickMs: 0` — deliberately, your
fourth-run double-driver fix. And `advancePipeline()` is invoked from exactly
one place, inside that timer's callback (`daemon.ts:314-329`):

```
const ceremonyTimer =
  gateService && emLoop && ceremonyTickMs > 0
    ? setInterval(() => { ... await advancePipeline(); ... }, ceremonyTickMs)
    : undefined;
```

`ceremonyTickMs: 0` → no timer → `advancePipeline` never runs → the two steps
that only live inside it are unreachable in a live run. The daemon's own tests
exercise them; `test:live` cannot.

## Suggested fix

Rather than adding two calls to `run.ts` and having the lists drift a third
time, expose the pipeline on the handle — e.g. `startDaemon` returns
`advancePipeline` (or `handle.tick()`), and `run.ts` calls that instead of its
own seven. One list, one place to add the tenth step. `ceremonyTickMs: 0` keeps
doing its job: it stops the *timer*, not the pipeline.

A regression test that would have caught it: assert the set of glue functions
`run.ts` drives equals the set `advancePipeline` drives.
