## BLOCKING

- **Failure path is untested.** `AttachService.createNode` (packages/daemon/src/attach/service.ts)
  explicitly promises: "The node is made either way; a failed start is a thread line, not a
  failed create." That's exactly the behaviour this ticket most needs proven, since a start
  failure must not lose the created node. But no test drives a start failure through
  `createNode` and asserts (a) the node still comes back, (b) a thread line with "could not
  start the agent: …" was appended, (c) the returned stream has no live session. The three new
  cases in `service.test.ts` ("T204: creating a node starts its agent") only cover the happy
  work-node/conversation-node paths and `start: false`; there's no analogous
  `attach: reject/throw` case (the file already has `SPEAKS_THEN_HANGS` and other scripted
  providers to build one from, or a provider that throws on `newSession`). Please add it before
  merge — this is the one code path in the whole change that's easiest to silently break later.

## NITS

- **Quick capture now defaults to `start: false`** (`packages/ui/app/components/TopBar.tsx`),
  overriding the ticket's "starts unless `--no-start`/"Start later"" default for the one entry
  point that doesn't offer a "Start later" checkbox. That's a reasonable product call (a jotted
  one-liner probably shouldn't spin up an agent), but it's not called for by the T204 ticket
  text, not mentioned in `design/projects-design.md` (quick capture there is only about which
  *project* it files into, P2), and isn't asserted by any test — the existing T162 quick-capture
  e2e tests don't check session state before or after this change. If this is intentional,
  worth a line in the ticket Notes and a test asserting the capture creates zero sessions;
  otherwise it should default to the normal "starts" behaviour like every other `node new` path.
- **P5 "node" step**: `design/projects-design.md` P5 lists the order as
  "flag or picker → node → project → repo → home → built-in", i.e. a node-level step distinct
  from the project step. This ticket only implements the project step (`resolveSessionSettings`
  gained `project`, not a per-node `session`), which matches the ticket's own scope ("The
  session defaults order gains the project step (P5)") — there is no per-node `session` field
  in the schema yet to resolve from, so this is not a gap in this ticket, just worth flagging
  so it isn't mistaken for "P5 done" in the design's fuller sense.
- **No vendor-spawn risk**: confirmed all new/changed tests attach only through
  `fakeProviderFor(...)` / the fake-agent transport (`runner/fake-agent`), never a real vendor
  binary. Fine.
- **T209 overlap**: `T209-repo-view` (in review in parallel) also adds a `describe(...)` block to
  `packages/daemon/src/feed/control-room.e2e.test.ts` right after the same anchor point (end of
  the T208 "left rail" describe, ~line 1992). `git merge-tree origin/claude/phase-7
  origin/T204-start-on-create origin/T209-repo-view` shows a textual conflict there (not a
  semantic one — both just append a new `describe` block). Whichever of T204/T209 merges second
  will need a one-line manual resolve to keep both blocks; no action needed on this branch.
