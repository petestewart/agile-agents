## BLOCKING

1. **`node list --json` shape is inconsistent, contradicting the ticket's own stated goal.** In `packages/cli/src/commands/stream.ts::runStreamList`, the change to a bare array (`printJson(nodes)`, with the comment "a bare array, so `jq '.[] | …'` reads it") only applies on the `--project`/`--parent` filtered branch. The **default** `node list --json` (no filters — the common case) still hits the original `printJson({ ...result, tree })` path further down, i.e. a nested `{tree: StreamNode[]}` shape where each entry is `{stream, children}`, not a flat node array. So `agile node list --json | jq '.[] | .id'` works only when you pass `--project` or `--parent`, and produces a different, incompatible shape otherwise. This is untested (the e2e/unit tests for `node list --json` only exercise the `--parent`/`--project` path — `stream.e2e.test.ts:109,113,444`) and looks like an oversight rather than an intentional split. Worth a follow-up: either flatten unconditionally, or drop the "bare array" framing from the comment/ticket note.

## Correctness vs §7 / ticket

- **Three reshapes vs §7**: matches the table exactly and is well tested in `repo-in-place.test.ts`:
  - conversation → work: branch + worktree created, thread preserved (`bodies` check), role transition verified.
  - work → coordinating: `splitWorkNode` moves branch/worktree/**sessions** into the new "<repo> part" child; test confirms the moved branch's HEAD still has the commit made before the reshape (`git rev-parse work.branch` in the *origin* repo, not just the worktree — a real check that the branch wasn't left dangling) and that session ids carry over unchanged.
  - switch-with-nothing-committed: reshapes then closes the empty part (worktree removed via `removeWorktreeSafely`, branch force-deleted, node closed); verified via `existsSync` and `human.status`.
  - A live session is correctly stopped before the reshape and restarted after (both for the plain add-repo path and the split path); tests check `sessions[0].status === 'stopped'` and a fresh session attached in the new worktree/coordinator context. Restart failure is caught and posted as a thread event rather than throwing, which is reasonable — the reshape itself has already committed to disk by that point.

- **Switch semantics ("nothing committed")**: `assertNothingCommitted` checks both `rev-list --count main..branch` (commits ahead) and `git status --porcelain` in the worktree (uncommitted changes). This is stricter than the ticket text ("nothing committed") — it also refuses on dirty working tree, which is correct and safer (an uncommitted diff would otherwise be silently discarded when the worktree is removed). Good.

- **Non-transactional multi-step reshape**: confirmed by reading `splitWorkNode` — it is genuinely non-atomic: (1) create the "from" part via `newPart` (a `streams.create` + `appendThread`), (2) copy branch/worktree/sessions onto it, (3) clear those fields off the parent node, (4) create the "to" part. There is no rollback if the process crashes between these steps (e.g. after step 1 but before step 2, an empty orphan "api part" child is left with no branch/worktree while the original node still holds them — `nodeRole` would already report the node as "coordinating" once any live child exists, per `packages/shared/src/stream.ts:551-559`, so the node would show a stale/inconsistent "coordinating-but-still-has-a-repo" state). This is a real recoverability gap: nothing in the code or docs describes how an operator would repair such a partial reshape, and there's no test exercising a simulated mid-failure. Given each individual `store.updateStream` call is a single validated file write (so no single step half-writes), the exposure is narrow (only a process crash/kill between two RPC-local awaits), but it is still unhandled. Not blocking given the low likelihood and that no other reshape-shaped code in this codebase has transactional rollback either (precedent), but worth a follow-up ticket/note — the module's own doc comment even hints at the ordering concern ("Stop first, so the exit path writes onto the records before they move") without addressing the multi-step-write risk.

- **`node list --json` (bare array) / `node show --json` (flattened)**: `node show --json` change is fine — it spreads the stream's fields at the top level and *keeps* the nested `stream` key for older readers (confirmed: `stream.e2e.test.ts:377` and `:336` still parse `{stream: Stream}.stream...` successfully). No caller broken. `node list --json`, however, has the inconsistency above (BLOCKING #1). No other callers were found in the codebase (checked `status.ts`, `test-support.ts`, UI `api.ts` — none parse `node list --json` output).

- **Stopped-then-restarted live session**: handled via `wasLive` snapshot before `sessions.stop`, then `sessions.attach` after the reshape completes, with restart failure caught and logged to the thread rather than thrown (so the reshape itself isn't rolled back by an attach failure — reasonable, matches "Parts are not started" note). Covered by the `'a live conversation session is restarted...'` and `'work + web: coordinating...'` tests, which check `attach.handleFor(node.id)` is defined afterward.
